> **One-liner**: Each person signs in with their own account via Microsoft 365 (OIDC) with MFA, or a local account with passkey, and gets analyst, senior, admin or auditor rights.

## Description

### Context

One env-seeded admin (PR #9). No way to tell who did what; no MFA; revoke means rotating the key.

### User Flow Impact

Sign in with Microsoft button; admin page lists users.

### Performance / Efficiency Impact

Server-side session lookup per request; negligible.

### Proposed Approach

1. ADR for OIDC (Authlib, BSD) and session store
2. User table per tenant, roles
3. Server-side sessions with idle timeout and revoke
4. Keep env admin as break-glass

### Risks & Follow-ups

Auth change: needs Ale's per-PR approval (rule 9). DB schema is a shared contract. Plan: "FeeLens: going live with client data" (project doc, 2026-11-12).

## Acceptance Criteria

- [x] #1 A user of tenant A cannot read tenant B, and a revoked session is refused on the next request (done in SC-11.12, PR #62)
- [x] #2 Existing env admin sign-in keeps working as break-glass (regression guard)
- [x] #3 With a key set, sign-in needs a valid code; a code works once; a forged key is refused
- [x] #4 `PCE_REQUIRE_MFA=1` keeps an account without a key out of client data until it adds one

## Implementation Notes

- Scope narrowed (2026-11-25): named users, roles and server sessions shipped in SC-11.12 (PR #62). OIDC
  dropped for now, as in the closed PR #48, so there is no Microsoft 365 dependency; this story is the TOTP
  second factor, ported from #48 (Ale chose "close #48, port the good parts" and released its claims).
- Key stored in a new table `user_mfa` (shared contract, rule 4), so `user_account` needs no migration.
- Stdlib only (hmac, base64): no new dependency.
