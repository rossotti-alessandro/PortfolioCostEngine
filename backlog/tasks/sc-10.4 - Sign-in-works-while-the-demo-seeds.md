> **One-liner**: Signing in during the first minutes after a deploy fails with a server error, because the demo seed holds the SQLite write lock for its whole run.

## Description

### Context
With `PCE_AUTOSEED=1` (the Render demo) a background thread seeds the SYNTHETIC prospects. `seed_demo`
ingests about 15 documents (one is an OCR scan) in a single transaction and commits once at the end, so
the SQLite write lock is held for the whole seed (1-2 minutes on the Render free plan). Sign-in writes a
server session row (`auth_session`, SC-11.12) and fails after SQLite's default 5 s wait with
`database is locked`, so the person gets HTTP 500. Reproduced locally on main ad94e5f: a login 10 s after
start returned 500.

### User Flow Impact
The first sign-in after every deploy or free-plan wake-up works instead of failing.

### Performance / Efficiency Impact
One commit per seeded document instead of one in total: negligible.

### Proposed Approach
1. `seed_demo`: commit after creating each prospect and after each ingested document, so the lock is
   free while the next document is being read.
2. `make_session_factory`: SQLite busy timeout 30 s (default 5 s) so a short write overlap waits
   instead of failing.

### Risks & Follow-ups
Seeding becomes visible document by document (a prospect may briefly show fewer documents). Seeding is
idempotent per document, so a crash mid-seed resumes on the next start.

## Acceptance Criteria

- [ ] #1 A sign-in during a slow seed returns 200 (test with a slowed extractor).
- [ ] #2 Seeding twice still adds nothing the second time (existing test stays green).
