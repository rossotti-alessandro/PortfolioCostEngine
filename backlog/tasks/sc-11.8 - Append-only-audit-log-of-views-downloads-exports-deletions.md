> **One-liner**: Record who viewed, downloaded, exported or deleted which prospect's data and when, so a breach can be scoped and FINMA/FDPIC questions answered.

## Description

### Context

Only review actions are logged; document views and downloads are not.

### User Flow Impact

Senior and auditor roles see an activity page per prospect.

### Performance / Efficiency Impact

One insert per request on prospect routes.

### Proposed Approach

1. Audit table (tenant, user, action, prospect, document, at), no content
2. Middleware on prospect/document routes
3. Hash chain so edits are detectable

### Risks & Follow-ups

Schema is a shared contract; serialise with SC-11.7. Plan: "FeeLens: going live with client data" (project doc, 2026-11-12).

## Acceptance Criteria

- [x] #1 Viewing, downloading and exporting a synthetic document each add one audit row with no document text
- [ ] #2 Tampering with a past row is detected by the chain check (regression guard)

## Implementation Notes

AC #2 changed: a hash chain conflicts with erasure (SC-11.11 deletes a prospect's earlier entries, which would break any chain). Instead a database trigger refuses any UPDATE of audit_event (tested). Someone with direct file access can still alter the database; the encrypted disk and backups cover that. Needs Ale's confirmation of the change.

## Outcome

Audit entries added for prospect opened and document viewed (ids only), on top of existing writes, report downloads, sign-ins and failed authenticator codes. audit_event rows cannot be updated (SQLite trigger). Tests: tests/test_audit.py (2), tests/test_accounts.py.
