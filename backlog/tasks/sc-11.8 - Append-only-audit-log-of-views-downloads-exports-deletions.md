> **One-liner**: Record who viewed, downloaded, exported or deleted which prospect's data and when, so a breach can be scoped and FINMA/FDPIC questions answered.

## Description

### Context

Only review actions are logged; document views and downloads are not.

### User Flow Impact

Senior and auditor roles see an activity page per prospect.

### Performance / Efficiency Impact

One insert per request on prospect routes.

### Proposed Approach

1. Audit table (tenant, user, action, prospect, document, at), no content
2. Middleware on prospect/document routes
3. Hash chain so edits are detectable

### Risks & Follow-ups

Schema is a shared contract; serialise with SC-11.7. Plan: "FeeLens: going live with client data" (project doc, 2026-11-12).

## Acceptance Criteria

- [x] #1 Viewing, downloading and exporting a synthetic document each add one audit row with no document text
- [x] #2 Tampering with a past row is detected by the chain check (regression guard)

## Implementation Notes

- Shared contracts touched (rule 4): `db.py` gains one new table `audit_seal`; `permissions.py` gains `audit.read`
  (admin, viewer, senior). `audit_event` itself is unchanged (no migrations: `create_all` adds the new table).
- A hash chain (prev hash) was replaced by one HMAC seal per row plus id-gap detection: concurrent writers
  cannot fork it, and a deleted row still shows as a gap. The seal is written by a SQLAlchemy `after_insert`
  hook, so the ~30 existing `audit(...)` call sites (API, CRM, admin) are covered without edits.
- Claim: the previous claim (2026-11-13, thread "Make FeeLens production ready for client data", PR #48 still
  open and bundling SC-11.7/11.8/11.11) was stale; released with Ale's explicit OK on 2026-11-25. PR #48 also
  has a view-audit design; whichever merges second must reconcile (an erasure job must keep audit rows, which
  hold ids only).

## Outcome

Every `audit_event` row is sealed (HMAC, key `PCE_AUDIT_KEY` else `PCE_SECRET_KEY`). New events: sign-in,
failed sign-in (known usernames), sign-out, password change, document and spreadsheet views, reading the
log. `GET /api/audit` returns the firm's events (filters: person, kind; paging) and a tamper check that
reports edited rows, rows inserted by hand and deleted rows; other firms' rows are never shown. "Activity
log" page (EN/IT, phone-safe) for admin, viewer and senior. Tests: `backend/tests/test_audit.py` (5),
`frontend/tests/e2e/activity.spec.ts`. Known limit (SECURITY.md): someone with DB write access and the key
can forge seals; a write-once copy (backups) closes it.
